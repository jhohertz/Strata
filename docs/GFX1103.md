Status: **implemented, Phase A and Phase B verified on the target machine
(2026-09-30), rebased onto Engine 0.1.31 (2026-10-01, §11).**  The §4 changes
are in (adapted to the 0.1.31 arch-gate structure), the gfx1103 build passes

## 2. Why "just open the build gate" is not enough

gfx1103 shares the RDNA3 ISA with gfx1100 (wave32, 64 KiB LDS, `v_dot`/dp4a,
WMMA), so **no kernel algorithm changes are needed**. But the codebase
deliberately validates the *specific architecture* in several independent
places — a binary built for gfx1100 will not load on gfx1103, so the gates
exist to stop silent misruns. Each one must be opened (or the build/execution
fails, or — worse — runs on a slow fallback path):

| # | Location | What it does | What happens on gfx1103 as-is |
| --- | --- | --- | --- |
| 1 | `cmake/hip_backend.cmake:6-9` | `FATAL_ERROR` unless `CMAKE_HIP_ARCHITECTURES` is exactly `gfx1100` | configure fails (this is the gate that was tried) |
| 2 | `include/strata/hip_compat/intrinsics.hpp:18` | fast `__dp4a` via `__builtin_amdgcn_sudot4`, guarded by `defined(__gfx1100__)` | compiles, but **every quantized dot product silently takes the scalar fallback** — a large decode-speed loss, invisible without benchmarks |
| 3 | `src/core/device.cu:69` | runtime gate: `gcnArchName` must start with `gfx1100` (7 chars) and wave32 | engine refuses to start: "HIP backend requires validated gfx1100 wave32 hardware" |
| 4 | `setup.py:709` | `AMD_ARCHS = ("gfx1100",)`; `amd_problem()` rejects other archs | installer lists the GPU as "not supported … this is gfx1103" |
| 5 | `setup.py:710, 1728` | display name for unknown-product sysfs; failure message | cosmetic |
| 6 | `tools/hip/gfx1100-hipblaslt-*.txt` + `src/prefill/gemm.cu` | calibrated hipBLASLt solution table; loader **rejects** a table whose arch or hipBLASLt version doesn't match | no gfx1103 table exists → dense prefill GEMM falls back to plain `hipblasGemmEx` (correct, slower). The gfx1100 table is *not* reusable: solution IDs are per-arch per-library-version |
| 7 | `CMakeLists.txt:36`, `src/core/device_main.cpp:37`, `src/prefill/ggml_cuda_host.cu:33`, `src/kernels/cuda/fused_gr.cu:183`, `src/kernels/cuda/native_qsa_score.cu:144`, `docs/AMD_HIP.md` | help text / report lines / comments naming gfx1100 | cosmetic, but should be updated so the tree tells the truth |

Note the shape of the risk: items 1, 3 and 4 fail loudly (easy), item 2 fails
**silently in performance**, item 6 degrades perf with a graceful fallback.
That is why the work is "open several gates + calibrate one table + update
the docs", not a one-line patch.

## 3. What already works on gfx1103 (verified, no changes needed)

- **Pinned llama.cpp ggml-cuda** (fetched commit
  `3cf03257f219afbe7334045ff7c6a06ac68c627d`, the exact revision CMake builds):
  - Runtime cc for gfx1103 is `0x01001103`, which falls inside
    `GGML_CUDA_CC_IS_RDNA3_0(cc)` (`>= 0x01001100 && < 0x01001150`) and
    `GGML_CUDA_CC_IS_RDNA3(cc)` — the *same* bucket as gfx1100.
  - `amd_wmma_available(cc)` and `bf16/fp16_mma_hardware_available(cc)` are
    true for it → the WMMA-based MMQ kernels are selected at runtime, same as
    gfx1100.
  - Compile-time path: `ggml-cuda/vendors/hip.h` defines `RDNA3` from the
    compiler family macro `__GFX11__`, which this clang defines for gfx1103
    too → `RDNA3`/`RDNA3_0` macros and the `mmq-config-rdna3.cuh` configs
    compile in unchanged.
  - `ggml_cuda_should_use_mmq` (mmq.cu:266): with `n_experts >= 64` (this
    model: 512) MMQ is used for the IQ types — identical decision to gfx1100.
  - Strata's `ggml_cuda_parse_amd_id` (`src/prefill/ggml_cuda_host.cu`) already
    parses arbitrary `gfxXXXX` names; `0x01001103` is produced correctly.
  - `d.integrated` is hardcoded `false` for HIP, matching upstream llama.cpp
    (which disables the integrated flag there too, "temporarily disabled due
    to issues with corrupted output").
- **LDS-sensitive kernels**: `fused_gr.cu` uses `TILE = 1280` on HIP because
  "eight-token tile fits gfx1100's 64 KiB LDS limit". gfx1103's LDS is the
  same 64 KiB → no change.
- **QSA scorer**: the HIP path is an ordered scalar FP32 fallback,
  arch-independent.
- **Expert-cache sizing**: `--expert-cache auto` sizes from
  `cudaMemGetInfo` free bytes minus reserves, and the code already carries a
  16 GB-card path (#199: the MTP draft-head bytes are reserved before the
  cache is sized). 16 GiB GTT is handled by existing logic.
- **hipBLASLt dispatch** (`src/prefill/gemm.cu`): per-arch + per-version
  validation with a documented fallback to `hipblasGemmEx`; the test
  `hip_prefill_hipblaslt_gemm` self-skips (exit 77) when no matching table is
  provided. Nothing breaks without a gfx1103 table; it just isn't calibrated.
- **Installer detection**: `setup.py amd_gpus()` decodes KFD
  `gfx_target_version 110003` into `gfx1103` with its existing format string —
  detection already works; only the support list (item 4) rejects it.

## 4. Required changes (exact)

### 4.1 `cmake/hip_backend.cmake` — accept the RDNA3 pair, stay strict

```cmake
# before
if(NOT CMAKE_HIP_ARCHITECTURES STREQUAL "gfx1100")
  message(FATAL_ERROR
    "Strata HIP currently supports only gfx1100 wave32; CMAKE_HIP_ARCHITECTURES is '${CMAKE_HIP_ARCHITECTURES}'")
endif()
# after
if(NOT CMAKE_HIP_ARCHITECTURES STREQUAL "gfx1100" AND NOT CMAKE_HIP_ARCHITECTURES STREQUAL "gfx1103")
  message(FATAL_ERROR
    "Strata HIP supports RDNA3 wave32 (gfx1100, gfx1103) only; CMAKE_HIP_ARCHITECTURES is '${CMAKE_HIP_ARCHITECTURES}'")
endif()
```

(plus the two comment lines at the top of the file). Do **not** make it a
free-form list: every new arch needs validation, so the gate stays a closed
set.

### 4.2 `include/strata/hip_compat/intrinsics.hpp:18` — the silent perf gate

```cpp
// before
#if defined(__gfx1100__) && __has_builtin(__builtin_amdgcn_sudot4)
// after
#if (defined(__gfx1100__) || defined(__gfx1103__)) && __has_builtin(__builtin_amdgcn_sudot4)
```

`__has_builtin` keeps it safe if a future clang drops the builtin for a target.
The header comment ("…that HIP does not provide on gfx1100") becomes "on RDNA3".

### 4.3 `src/core/device.cu` — runtime validation gate

```cpp
// before (lines ~66-71)
    // backend is validated on gfx1100 (wave32) only.
#if defined(STRATA_USE_HIP)
    if (std::strncmp(p.gcnArchName, "gfx1100", 7) != 0 || p.warpSize != 32) {
        throw CudaError("HIP backend requires validated gfx1100 wave32 hardware", -1);
    }
// after
    // The HIP backend is validated on RDNA3 wave32 hardware: gfx1100 (RX 7900
    // series) and gfx1103 (integrated). Match the validated pair exactly: a
    // gfx1103-only binary must not claim to run on other RDNA3 parts.
#if defined(STRATA_USE_HIP)
    const bool validated = std::strncmp(p.gcnArchName, "gfx1100", 7) == 0 ||
                           std::strncmp(p.gcnArchName, "gfx1103", 7) == 0;
    if (!validated || p.warpSize != 32) {
        throw CudaError("HIP backend requires validated RDNA3 wave32 hardware "
                         "(gfx1100 or gfx1103); device reports " +
                         std::string(p.gcnArchName), -1);
    }
```

Also update the line-34 "no HIP device" message to name the RDNA3 pair.

### 4.6 `tools/hip/` — calibrate a gfx1103 table (done, 2026-09-30)

Not a code change. The existing tuner was run on this machine with the
engine's actual prefill shapes **plus** the two focused shapes that
`hip_prefill_hipblaslt_gemm` requires (`closest()` matches `N,K,ldy` exactly):

```sh
build-hip/tune_hipblaslt --tuning-out tools/hip/gfx1103-hipblaslt-100401.txt \
  --case f16,8192,10240,2560,10240 \
  --case f16,8192,320,10240,320 \
  --case f16,8192,2560,320,2560 \
  --case bf16,8192,10240,2560,10240 \
  --case bf16,8192,320,10240,320 \
  --case bf16,8192,2560,320,2560 \
  --case bf16,4096,48,2560,96   --case bf16,37,48,2560,96 \
  --case f16,4096,512,2560,512  --case f16,37,512,2560,512
```

Result: `tools/hip/gfx1103-hipblaslt-100401.txt` (9 rows; `100401` is this
install's hipBLASLt library version, distinct from the gfx1100 tables' 100100/
100200). Findings from the calibration:

- **f16 tuned 2.3–4.0× faster than the `hipblasGemmEx` baseline** on all three
  model shapes (ISA1103 Tensile solutions; solution id 5992).
- **bf16 MoE shapes tuned** (320×10240, 2560×320; solution 5387).
- **bf16 dense shape (10240×2560×8192): every hipBLASLt heuristic returns
  NaN on this stack** and is rejected by the tuner's accuracy gate — the
  table has no row, so the engine falls back to plain `hipblasGemmEx` for that
  shape. The fallback is correct (verified against a CPU reference, max rel
  error 2.1e-5) but untuned. This is a ROCm 10.0pre/rocBLAS gfx1103 bug to
  track upstream, not a Strata issue; the accuracy gate is exactly what it is
  for. (The f16 dense shape works via Lt, so nothing is blocked.)

## 5. Build on this machine

```sh
cmake -S . -B build-hip \
  -DCMAKE_BUILD_TYPE=Release \
  -DSTRATA_ENABLE_HIP=ON -DSTRATA_ENABLE_CUDA=OFF \
  -DSTRATA_PREFILL_MMQ=ON \
  -DCMAKE_HIP_ARCHITECTURES=gfx1103 \
  -DCMAKE_PREFIX_PATH=/opt/rocm
cmake --build build-hip -j16
```

Notes:

- `STRATA_PREFILL_MMQ=ON` matches the measured RX 7900 XTX configuration
  (HIP MMQ for the prompt path). It pulls the pinned llama.cpp ggml-cuda MMQ
  sources; expect CMake to fetch that commit on the first configure.
- **`-DCMAKE_PREFIX_PATH=/opt/rocm` is required on this machine**: without it
  CMake finds the *distro's* `hip`/`hipblas`/`hipblaslt` configs under
  `/usr/lib/x86_64-linux-gnu/cmake` (7.1-generation ROCm, no gfx1103 rocBLAS
  kernels) and the first GEMM aborts at runtime. See §9.9.
- `cmake/hip_backend.cmake` now pins the build tree's rpath to the ROCm lib
  directory it configured against (the `/opt/rocm` libraries carry `$ORIGIN`
  rpaths that keep the rest of the tree together), so the binaries run
  correctly with no `LD_LIBRARY_PATH`.
- The system ROCm in `/opt/rocm` has `bin/hipcc`, `lib/libhipblas.so*` and the
  CMake configs, so `setup.py` will use it directly (no ~10 GB TheRock wheel
  install; the wheel index is a dgpu one anyway).
- If CMake picks the wrong compiler, pin it:
  `-DCMAKE_HIP_COMPILER=/opt/rocm/core-10.0/lib/llvm/bin/amdclang++`.
- Build everything, not just `strata` (the parity targets are the validation).
- **Never build or run this tree with `HSA_OVERRIDE_GFX_VERSION` set.** With a
  gfx1100 override the runtime arch name would read `gfx1100`, the §4.3 gate
  would pass, but a gfx1103-only binary would then hit driver-level mismatches
  at launch. The override was a crutch for *other* software; Strata supports
  the real arch directly.

## 7. Serving configuration for this machine

The transfer was `Qwen3.8-Flash-Next` GSQ-RCO **Q2_0** (native/IQ pack). The
smoke checks run in one-shot generate mode via
`tools/hip/gfx1103_smoke.sh` (§6); the serve line, for when the MTP draft-head
GGUF arrives (`--mtp` is mandatory for `--serve` and is not in the transfer):

```sh
STRATA_HIPBLASLT_TUNING=$PWD/tools/hip/gfx1103-hipblaslt-100401.txt \
build-hip/strata --serve \
  --pack packs/qwen38-flash-next-q2_0 \
  --native /home/jhohertz/models/ISTA-DASLab/Qwen3.8-Flash-Next-GSQ-RCO-GGUF/Q2_0/Qwen3.8-Flash-Next-GSQ-RCO-Q2_0-00001-of-00002.gguf \
  --ple-gguf /home/jhohertz/models/ISTA-DASLab/Qwen3.8-Flash-Next-GSQ-RCO-GGUF/Q2_0/Qwen3.8-Flash-Next-GSQ-RCO-Q2_0-00002-of-00002.gguf \
  --mmap-experts \
  --expert-profile data/expert-profile.bin --expert-cache 6000 \
  --prefill 512 --spec 4 --spec-min-p 0.5 --mtp mtp/rt \
  --max-context 4096 --kv int8 --pool-workers 8 \
  --adapt-every 0 --pcie-frac 0 --vram-reserve-mib 1024
```

Rationale, iGPU-specific:

- **`--mmap-experts` is mandatory, not optional here.** The memlock rlimit is
  8 MiB (`ulimit -l 8192`), so large pinned host arenas cannot be registered;
  the mmap path was designed for exactly this. Raising memlock
  (`LimitMEMLOCK=` on a service unit, or root `prlimit`) is a possible
  experiment, but mmap + file cache on the NVMe is the supported path.
- **No `--resident-cpu-experts` on this box.** Its own check refuses: the
  resident complement (~24 GiB) plus the pack's page cache exceeds available
  RAM minus its 8 GiB safety headroom. The non-resident mmap-on-demand expert
  path is the supported low-RAM mode here.
- **Explicit `--expert-cache 6000` (~7.72 GiB), not `auto`.** `auto` sizes
  from the HIP runtime's 22.86 GiB figure (§9.2) and requests ~17 GiB, which
  faults on the real ~16 GiB GTT and poisons subsequent allocations. 6000
  slots fits with headroom and pre-fills from the profile ("slot 0
  verified").
- **`--pool-workers 8`** to start (16-core CPU that also drives the display;
  the XTX reference used 15 on a 16-core desktop CPU). Measure, don't assume.
- **`--prefill 512`, `--max-context 4096`** to start. Long context is not a
  first-day target on a 12-CU iGPU; revisit after the first numbers.
- **Model fit (Q2_0):** experts live mmap'd on the NVMe (31.64 GiB
  `experts.bin`), the dense weights 1.48 GB and the PLE table 607 MB sit in
  the GTT/VRAM budget, the token embedding (260 MB) in mapped host memory.
  The GTT is shared with the display stack (~182 MiB at idle), which
  `--vram-reserve-mib 1024` keeps out of the engine's hands.

## 8. Performance expectations (pre-measurement, to be confirmed)

Reference: RX 7900 XTX (60 CU, HBM3 ~960 GB/s) does ~900 t/s prefill and
~56-59 t/s decode on the measured configuration. This iGPU has 12 CU (5x
fewer) and DDR5-class GTT bandwidth (~70-90 GB/s, ~10-13x less):

- **Prefill**: order-of-magnitude 30-100 t/s → a 4,200-token prompt takes
  minutes, not seconds. Usable for interactive work with patience; the
  batched-prefill path (MMQ) is what makes it tolerable.
- **Decode**: bandwidth-bound on active expert weights read from GTT;
  roughly 10-25 t/s is the plausible band for the IQ3_XXS-class model,
  better with a larger resident expert cache. MTP speculation (`--spec 4`)
  should pay off more here than on the XTX because the CPU (16 cores) is
  relatively stronger against the GPU.

These are planning numbers only — Phase B measures the real ones.

## 9. Risks and open questions

1. **Newer toolchain than validated.** The backend was validated on
   ROCm 7.1.52802 / Clang 20; this machine has ROCm 10.0.0~pre4 / AMD clang 23.
   Mitigations: the parity test suite (Phase A) is the contract — in particular
   the Q8_K byte-exactness note in `AMD_HIP.md` (HIP's `__fmul_rn` contraction
   behavior) and the dp4a overflow checks. The hipBLASLt solution table is
   version-scoped by design, so no stale-table risk. **Phase A passed on this
   toolchain (32/32, §6), so the risk closed.**
2. **GTT size moved between scans.** The initial scan saw a 16 GiB cap despite
   `amdgpu.gttsize=49152`; after the driver/ROCm package update the HIP
   runtime reports 22.86 GiB, which the engine plans against. Either size is
   enough for the plan (expert cache auto-sizes).
3. **Misleading marketing names.** The driver/rocm-smi product string
   ("Radeon 780M") does not match the real part; the KFD
   `gfx_target_version` and `rocm-smi --showgfxversion` (gfx1103) are the
   sources of truth, and `setup.py` already uses KFD. Cosmetic only.
4. **`HSA_OVERRIDE_GFX_VERSION` hygiene.** It must not be present in the
   Strata environment (see §5). Recommend a line in `AMD_HIP.md`.
5. **memlock 8 MiB** blocks the non-mmap pinned paths and
   `platform_memory_test` (documented exclusion).
6. **Display co-residency**: the iGPU serves six display outputs; the engine
   and the compositor share the CUs and the GTT. The 1 GiB reserve and modest
   starting context are the mitigation; sustained load will also be
   power/thermal-limited on a laptop APU.
7. **One GPU only, no images, no calibration** — the existing HIP limits
   carry over unchanged.
8. **CU count disagreement (6 vs 12).** KFD topology reports 12 CU / 24 SIMD,
   but the HIP runtime on this ROCm reports 6 multiprocessors, and
   `strata-device` shows 6. This is a ROCm 10.0pre/driver quirk on this APU,
   not a Strata bug: the kernels are data-parallel (no CU-count tiling),
   correctness is unaffected, and `strata-device`'s plan uses the runtime
   value consistently. Watch it in Phase B — if prefill throughput looks
   limited, the real CU count (12) is the capacity ceiling, not 6.
9. **Dual ROCm installs on one machine.** The distro's ROCm (7.1-generation)
   lives under `/usr` and is first in the CMake and ldconfig search path; the
   ROCm 10.0 tree under `/opt/rocm` is the one with gfx1103 rocBLAS kernels.
   The build is pinned to `/opt/rocm` via `-DCMAKE_PREFIX_PATH` (§5) and the
   build tree's rpath is now set to the configured ROCm's lib directory by
   `cmake/hip_backend.cmake`, so the binaries load the matching libraries
   without `LD_LIBRARY_PATH`. A machine that hits "Cannot read
   TensileLibrary… for GPU arch : gfx1103" has this mismatch — configure
   against the ROCm that ships the device's kernels.
10. **bf16 dense GEMM: hipBLASLt NaN on this stack.** All eight hipBLASLt
    heuristic solutions for (N=10240, K=2560, T=8192) in bf16 return NaN on
    ROCm 10.0pre; the tuner's accuracy gate excludes them from the table and
    the engine falls back to `hipblasGemmEx`, which is correct (max rel error
    2.1e-5 vs a CPU reference) but runs untuned. The f16 dense shape is fine
    via Lt (3.15× the baseline), and the engine's dense projections are bf16,
    so the practical effect on this machine is an untuned dense GEMM —
    track the upstream fix, and re-run the tuner when the stack updates
    (solution ids are version-scoped anyway).
11. **Killing a HIP process mid-GPU-work wedges the GPU; only a reboot
    recovers it (no root on this box).** Observed 2026-07-22: after the
    engine was SIGKILLed while running the prompt path, every subsequent HIP
    process — including a 4-byte kernel + D2H probe — hung forever (runtime
    spin, `rocm-smi` at 99% GPU use with **no** KFD client, no D-state
    process, no memory pressure). Isolated probes confirmed the wedge covers
    every copy source class (pinned, anon-pageable, file `MAP_PRIVATE`/`MAP_
    SHARED` — the latter segfaults) and size (8 MiB … 1.3 GiB, hot or cold
    page cache, warmup kernel first or not). The wedged state is intermittent:
    one run between wedges completed ~63 H2D copies before hanging again.
    **Rules for this machine:** never kill a HIP process while GPU work is in
    flight (let runs finish, or use the engine's graceful cancel / a timeout
    only on already-dead runs); run one HIP process at a time; if the GPU
    wedges, do not trust partial windows — reboot. `dmesg` is unreadable
    without root, so the exact driver fault is unconfirmed; if root access
    ever lands, capture `dmesg` immediately after a wedge.
12. **H2D reliability before the wedge was not clean either.** The first
    smoke run (16:10, minutes after the successful 15:52 session) hung in the
    first weight upload; the successful 15:52 session had uploaded ~10 GB of
    H2D traffic fine. This is consistent with the wedge having started at the
    kill, but not provable. As a hedge, `WeightTable::load` gained a
    `STRATA_PAGEABLE_STAGING=1` switch (pageable staging instead of pinned;
    inert unless set).  Post-reboot A/B (2026-09-30 01:32, warm page cache):
    the pageable arm completed weight load + full generation with **no H2D
    failure** and the correct answer (decode 8.57 vs 7.25 tok/s pinned,
    prefill 26.1 vs 8.2 tok/s) — but the pageable arm ran against a warm
    expert page cache (620 ms host streaming vs 3259 ms cold), so the speed
    delta is confounded and not attributable to the staging mode.  Verdict:
    keep the switch as a validated **fallback for flaky pinned H2D**;
    do not claim a speed benefit.
13. **Ad-hoc `clang++ -x hip` kernels fault; CMake kernels are fine (post-reboot,
    unexplained).** After the reboot cleared the §9.11 wedge, a hand-compiled
    probe's memory ops (H2D/D2D/D2H) worked but its trivial kernel
    (`p[0]=7`, one block) failed with "an illegal memory access was
    encountered", while CMake-built kernel binaries (`hip_intrinsics`,
    `strata-device`) ran correctly in under 0.1 s. The smoke driver's GPU gate
    therefore uses `build-hip/hip_intrinsics` instead of a fresh probe compile
    (a fresh one would false-alarm on a healthy GPU). If the difference is ever
    pinned down (a compiler flag or code-object version), the gate can go back
    to a self-contained probe.
14. **Rapid back-to-back engine sequences degrade KFD for hours (post-reboot,
    2026-09-30 evening).** After the first post-reboot smoke pass (19:47–19:49,
    clean, 4/4) a performance A/B driver ran eight engines in quick succession;
    two of them died mid-run (one segfault during weight load, one
    `cudaMemcpy` failure) and both were killed.  From that point until the next
    reboot the box stayed in a degraded state that the `hip_intrinsics` gate
    does not catch: small kernels and even `strata-device`'s 5.9 GiB pool
    allocation kept passing, while engine runs intermittently failed —
    `ExpertCache: cudaMalloc(7.72 GiB) failed: unspecified launch failure`, a
    7-minute userspace spin after the weight load, and finally a
    `prefill copy_i32: unspecified launch failure` followed by a **bus error**
    (exit 135, SIGBUS — consistent with a fault in the 28.8 GB mmap'd PLE table
    or the 31.6 GiB `experts.bin` mapping once the GPU state is corrupt).
    The `strata-device`/`hip_intrinsics` gates are necessary but not sufficient
    on this machine; treat any engine crash or mid-run kill as the start of a
    degraded window and stop running engines (reboot to recover).  This is why
    the remaining A/B measurements (`STRATA_PAGEABLE_STAGING`, tuned-vs-untuned
    prefill) were parked until a reboot rather than risked against a degraded
    KFD.  Confirmed post-reboot (01:26–01:33): a fresh 4/4 smoke pass plus
    both A/Bs ran back-to-back with 60 s cooldowns and zero GPU faults — the
    reboot fully restores the box, and the one-process-at-a-time + no-mid-run-
    kill + no-rapid-sequence rules keep it there.
